# ingot

**여러 축에서 동시에 이기는 것**을 목표로 만든 손실 이미지 코덱입니다. 압축률 하나만 보지 않습니다.

[English](README.md)

대부분의 코덱은 한 성질을 얻으려고 다른 성질을 내줍니다. ingot은 아무도 목표로 삼지 않아서 비어 있던 축을 골라, 그것을 포맷 자체에 못 박습니다.

- **비트 단위로 같은 결과** — 라이브러리에 부동소수점 연산이 0개입니다. 같은 그림을 두 번 압축하면 바이트까지 같습니다.
- **스레드 수가 파일에 실리지 않습니다** — 병렬 단위를 16배 잘게 나눠도 파일이 **1.4%**만 커집니다. 기존 표준은 같은 일에 3.7~8%를 잃습니다.
- **작습니다** — `src/`가 C99로 약 1,300줄입니다. libc 말고는 의존이 없습니다.
- **망가진 입력을 전제합니다** — 디코더는 오류 코드로 돌아가고 죽지 않습니다. 손상 파일 300개에 비정상 종료 0건입니다.
- **JPEG과 거의 같은 수준입니다** — 색차 옵션을 켜면 같은 화질에서 JPEG보다 **1.3% 큽니다**. WebP(+15%)·JPEG XL(+34%)·AVIF(+159%)에는 아직 뒤집니다.

```console
$ sh build.sh
built: ./ingot

$ ./ingot enc photo.ppm photo.igt 20
1404x936  q20  -> 362219 bytes (source 3941568, 9.19%)

$ ./ingot dec photo.igt out.ppm
decoded 1404x936

$ ./ingot rt photo.ppm 20
1404x936 q20 group 256  4:4:4 |   362219 B (  9.19%) | maxdiff  22 | PSNR  38.64 dB
```

입출력은 PPM(P6, 8비트)만 다룹니다. 다른 형식은 ffmpeg으로 바꿔 넣습니다.

## 지금 어디까지 왔나

여덟 축을 각각 쟀습니다. 수치는 AOM 공통 시험 세트 8장, 품질 여섯 단계, 기계 한 대, 2026-08-21 기준입니다.

| 축 | 상태 | 근거 |
|---|---|---|
| 결정성 | **확보** | 두 번 압축하면 바이트가 같습니다. `src/`에 부동소수점 0개 |
| 병렬성 | **확보** | 조각 64에서 1024로 바꿔도 크기 차이 1.4%, 화질은 완전히 같음 |
| 단순성 | **예산 잠금** | 디코더 1,500줄 이하, 외부 의존 0, 규격 문서 10쪽 이하 |
| 특허 자유 | 만료 기술만 | DCT(1974), 골롬(1966), 라이스(1979). **법률 검토는 아직 안 받았습니다** |
| 압축률 | **JPEG 수준** | 4:4:4 — JPEG +7.4%, WebP +20.1%, JXL +39.3%, AVIF +147.7%<br>4:2:0 — JPEG **+1.3%**, WebP +15.2%, JXL +33.5%, AVIF +159.3% |
| 인코딩 속도 | 주장 안 함 | 지금은 빠르지만 압축을 덜 해서 빠른 것입니다 |
| 디코딩 속도 | 미측정 | |
| 범용성 | 일부 측정 | 사진·화면 캡처·AI 생성 이미지·게임 스프라이트 |

색차 줄이기(4:2:0)는 기본으로 꺼져 있습니다. 켜면 사진에서 10.2%(PSNR)·13.2%(SSIM)를 벌지만, **화면 캡처에서는 8.5 dB를 잃습니다** — 글자의 색 경계가 무너집니다. 다섯 번째 인자로 `1`을 주면 켜집니다.

### 우리가 실제로 만드는 것으로 재면

우리가 실제로 다루는 이미지 12장(AI 생성·화면 캡처·게임 스프라이트 각 4장)으로 같은 방식으로 쟀습니다.

| 상대 | PSNR BD-rate | SSIM BD-rate |
|---|---|---|
| JPEG | **−4.0%** | +6.4% |
| WebP | +40.8% | +42.7% |
| JPEG XL | +34.1% | +52.1% |
| AVIF | +251.9% | +245.1% |

음수는 같은 화질에서 비트를 덜 쓴다는 뜻입니다. JPEG에 대해 두 지표가 서로 다른 답을 냅니다. 유리한 쪽만 고르지 않고 둘 다 적습니다.

## 압축률이 뒤진 것은 일부러입니다

성숙한 코덱이라면 다 가진 네 가지가 아직 없습니다. 논문 수치를 믿는 대신 **하나씩 넣으면서 각각이 얼마를 버는지 우리 손으로 재려고** 그렇게 뒀습니다.

1. ~~인트라 예측~~ — **2026-08-21 넣었습니다.** 네 모드(DC·세로·가로·평면), 블록마다 2비트, 인코더가 디코더처럼 복원합니다. PSNR 기준 −34.4%였습니다.
2. **지각 양자화 가중** — 지금 이 코덱에서는 이득이 0으로 측정됐습니다. 아래를 보십시오.
3. **크고 가변인 블록** — 8×8 고정입니다.
4. **산술 부호화** — 대신 적응형 골롬-라이스를 씁니다. 디버깅이 쉽습니다.

지금까지 하나씩 넣으며 잰 것입니다.

| 바꾼 것 | PSNR BD-rate | SSIM BD-rate |
|---|---|---|
| DC 예측 | −9.4% | — |
| 자리·평면별 양자화 가중 | −0.6% | −1.5% |
| 적응형 골롬-라이스 (무리 8개) | 누적 −11.7% | 누적 −10.4% |
| 0의 연속을 개수로 묶기 | **+6.2% (되돌림)** | **+6.6% (되돌림)** |
| 색차 줄이기 (옵션) | −10.2% | −13.2% |
| 인트라 예측 4모드 | **−34.4%** | **−21.0%** |
| 블록 머리말 적응 부호화 | q40에서 파일 −49%, q63에서 −58% | |

기록할 만한 결과가 둘 있습니다. **0의 연속을 묶는 방식은 오히려 나빴습니다** — 저주파는 계수가 대부분 0이 아니라서 "건너뛴 개수 = 0"이 비영 계수마다 1비트를 더 먹습니다. 그리고 **고주파 양자화 가중은 PSNR로도 SSIM으로도 순손해로 측정됐습니다.** 그래서 0으로 뒀습니다. JPEG의 양자화 표는 사람 눈을 상대로 맞춘 것이지 이 지표들을 상대로 맞춘 것이 아닙니다.

## 설계 규칙

- **SPEC.md를 먼저 고치고 코드를 고칩니다.** 고정 결과 파일이 깨지면 포맷이 바뀐 것입니다.
- 라이브러리에 부동소수점을 넣지 않습니다. 명령줄 도구의 화질 계산만 예외입니다.
- 예약 비트는 "무시"가 아니라 **"1이면 거절"**입니다. 안 그러면 옛 디코더가 새 파일을 조용히 잘못 그립니다.
- 지표 하나로 판단하지 않습니다. PSNR과 SSIM은 자주 다른 답을 내고, 그 차이 자체가 정보입니다.

## 구성

```
SPEC.md            비트스트림 규격 — 이것이 정본입니다
src/ingot.h        공개 C 인터페이스
src/transform.c    정수 8×8 DCT (표가 규격의 일부입니다)
src/color.c        RGB↔YCbCr 고정소수점
src/bitio.c        비트 입출력, 적응형 골롬-라이스
src/encode.c       인코더
src/decode.c       디코더 — 적대적 파서로 씁니다
tools/cli.c        명령줄 도구
tools/bench.py     BD-rate 측정 (PSNR·SSIM, 단조 보존 보간)
tools/compare.py   JPEG·WebP·AVIF·JPEG XL과 나란히 비교
test/run_tests.py  결정성·왕복·고정 결과·손상 입력
```

시험 이미지는 이 저장소에 없습니다. AOM 공통 시험 세트를 `media.xiph.org/video/aomctc/test_set/`에서 받아 ffmpeg으로 PPM으로 바꿔 쓰십시오.

## 언어에 대해

라이브러리와 `ingot` 명령줄 도구는 영어로 말합니다. **소스 주석과 `SPEC.md`, 그리고 `tools/`·`test/`의 개발용 스크립트는 한국어입니다** — 주석은 각 결정의 이유를 담은 기록이라 옮기면 뉘앙스가 죽습니다. 영문 규격서는 예정에 있고, 그때까지는 코드와 고정 시험 벡터가 정본입니다.
